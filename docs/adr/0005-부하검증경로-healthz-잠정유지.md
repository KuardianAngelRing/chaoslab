# ADR-0005: k6 부하 경로는 당분간 /healthz 유지 — ⚠️ 알려진 설계 오류, 재논의 필수

- 날짜: 2026-07-29
- 상태: **잠정 승인** (시웅 결정) — 팀 재논의 전까지의 임시 결정. 아래 "알려진 문제"가 해소된 게 아님.
- 재논의 트리거: **NetworkChaos 실험 실검증 착수 전**, 늦어도 **최종 발표 준비 전**

## 결정 (잠정)

- k3s 앱 등록 폼의 경로 필드는 구 방식 계승: **필수 + 기본값 `/healthz`**.
- 개명("부하 검증 경로")과 기능 경로 승격은 보류. k6는 기존대로 이 경로 하나에 부하를 보낸다.
- 이유: 지금 단계 목표는 UI 워크플로우 목업이고, pod-kill 시연은 이 설계로도 유효하게 굴러간다.

## 알려진 문제 — 왜 이게 설계 오류인가

측정 담당 k6가 요청을 보내는 주소가 healthcheck 경로(`/healthz`) 하나뿐이다.
`/healthz`는 "살아있어요"만 답하는 얕은 문이다(쿠버 probe 정석 — 일부러 의존성을 안 탄다).
식당 비유: 문지기에게 "영업 중이에요?"만 묻는다. 주방이 불타도 문지기는 "네"라고 한다.

1. **NetworkChaos 실험의 자기부정.** 서비스 사이(주문↔상품 API)에 지연을 일부러 주입해도
   `/healthz`는 그 경로를 안 탄다 → k6 측정 무변화 → 판정 "통과".
   **장애를 넣고도 측정기가 장애를 못 본다.** 실험 3종 중 1종이 무의미해진다.
2. **k6가 유일한 트래픽 소스다.** 실험 클러스터엔 실사용자가 없다. k6가 기능 경로를 안 타면
   열화된 경로를 지나는 요청이 0개 — Prometheus도 잴 것이 없다. 측정이 얕은 게 아니라 **부재**가 된다.
3. **AI 개선 루프 미발동.** 파이프라인은 판정 실패 → 원인 분석 → 패치 → 재실험 순서.
   측정이 "통과"로 거짓 보고하면 개선 루프가 "고칠 것 없음"으로 종료 —
   **자동 개선이라는 핵심 시연이 NetworkChaos에서 성립하지 않는다.**
4. **R지수 레이턴시 축(30%) 무효.** 중간보고서 확정 수식 R = 0.4·가용성 + 0.3·레이턴시 + 0.3·복구속도.
   현 설계로는 레이턴시 변화를 측정할 수 없어 0.3이 장식이 된다.
   발표에서 "레이턴시 점수는 어떻게 측정하셨나"는 질문에 답이 없다.

단, pod-kill류에는 유효하다: `/healthz` 연타로도 "장애 중 어떤 복제본이 응답하나"(가용성·복구 속도)는
정당하게 측정된다. 실제 smoke(pod-kill 복구 9.66s→3.37s) 판정이 이 설계로 작동했다.
또한 구의 판정은 k6 단독이 아니라 관측값 12개 체크(ready pods·재시작·복구시간)와 병행이다.

## 재논의 시 해결 후보

- **기능 경로 승격**: 필드를 "부하 검증 경로"로 개명, 기능을 대표하는 경로(예: `/orders`) 권장 안내.
  기본값은 manifest의 `readinessProbe.httpGet.path` 자동 추출 → 유저는 확인/수정만.
- k6 시나리오 다중 경로화(생존 경로 + 기능 경로 병행 측정)로 확장하면 가용성/기능성 분리 측정 가능.
- 논의 주체: 시웅(k6·판정) + 준영(분석·개선 루프) — 레이턴시 점수 산식과 직결.
