# ADR-0009: k3s 실험은 현장 배포 — 등록은 manifest 저장만

- 날짜: 2026-08-18
- 상태: 승인 (시웅 결정)
- 작성: 시웅 + Claude
- 관련: ADR-0002(환경은 앱 속성) · ADR-0004(일부 폐기) · ChaosPilot의 실험별 namespace 격리 패턴 흡수

## 맥락

기존 구조는 "앱을 먼저 배포하고, 배포된 앱을 대상으로 실험"(ADR-0004: k3s 등록=배포까지).
로컬(라즈베리파이 k3s)은 자원이 작고 셋이 공유하는 상시 클러스터라, 실험 대상을 상시로
띄워두는 것보다 실험할 때만 띄우는 편이 낫다. agent 레포(ChaosPilot)도 같은 이유로
실험마다 전용 namespace에 워크로드를 새로 배포했다 (클러스터의 `chaospilot-workload-*`
잔재가 그 흔적 — 단 ChaosPilot은 정리를 안 해 11개가 쌓여 있었음).

## 결정

**k3s 앱의 실험 대상은 실험 시작 시 현장에서 배포한다.** (EKS는 기존대로 상시 배포 대상 실험)

- **등록 = manifest 저장만.** ADR-0004의 "등록=배포까지"는 k3s에 한해 폐기.
  CTA는 "등록할게요", 앱 상태는 `registered`.
- **실험 파이프라인**: 전용 ns 생성(`chaoslab-{app}-{exp_id}`) → manifest apply →
  Deployment ready 대기 → Chaos CRD 주입(selector는 ns 전체 — 다중 서비스 manifest는
  서비스별 `app` 라벨이라 앱 이름 매칭 불가) → duration·회복 관측 → CRD 삭제 →
  **ns째 삭제** → completed. 실패·중지 시에도 ns 정리 (ChaosPilot의 잔재 문제 재발 방지).
- 실험 상태에 `deploying` 추가 (pending → deploying → running → completed/failed/stopped).

## 구현 지점

- `K3sWorkloadService`(Protocol) — deploy/wait_ready/teardown. Real은 SSH 터널 경유
  로컬 kubeconfig (`services/real/k3s_workload.py`), 게이트는 `LOCAL_KUBECONFIG`.
- `App.env`("eks"|"k3s", ADR-0002 백로그 해소) · `App.manifest` · `Experiment.namespace` 컬럼.
- `make_chaos(env, namespace)` — k3s는 로컬 kubeconfig + ns 전체 selector로 라우팅.
- 워처(`_watch_experiment`)가 k3s 분기에서 배포→주입→관측→정리 전체 수행.
